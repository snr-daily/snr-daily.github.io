## 研究

### 2. Google 与港大提出 VeriCUA：主动检查界面和文件，减少电脑操作的假完成判定

Google 与香港大学研究者提出 VeriCUA，让电脑操作验收从一次性看截图变成主动找证据。系统先检查环境或录屏，再将任务拆成可核对要求，选择界面或代码检查补齐未知项。它区分“Agent 声称完成”与“结果有证据支持”，信息不足时允许暂不判定。论文覆盖在线机器状态与离线记录，结果是作者评测，尚未在本机复现。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-31/2.svg" | relative_url }}" alt="VeriCUA 如何核对任务是否真的完成。查看环境并列出要求 → 主动补充结果证据 → 按规则决定或弃权" loading="lazy"></figure>

- 可用来源包括操作轨迹、无障碍树、机器快照和执行后状态。界面上出现修改后的文字，与文件已经保存，是需要不同证据支持的两件事。
- 仲裁器按固定证据规则聚合结果：所有硬性要求有支持才成功，有被证实未满足的要求则失败，仍不明确时按设定弃权或回退；执行者的完成消息不能单独证明成功。
- 在线对照统一使用 gemini-3-flash-preview；OSWorld 上，VeriCUA 总体准确率 79.5%，VLM judge 为 73.4%，假阳性率分别为 13.9% 和 27.9%。这不是操作 Agent 自身的任务成功率。
- 上述 OSWorld VeriCUA 只对 78% 案例作出决定，已决定部分准确率为 88.7%；总体指标把弃权计为失败，不能只报条件准确率而隐藏覆盖率。
- AndroidWorld、OSWorld 和 ScienceBoard 的在线实验与离线 WebArena、OSReward 分开评估。参考标签也可能出错，作者的标签争议分析不是人工全面重标的结论。

**为什么值得关注：** Agent 验收应围绕保存结果、记录和副作用取证，不能只相信结束语。允许弃权有助于减少误报成功，但会降低可自动处理的覆盖率并增加检查成本。

来源：[VeriCUA：论文方法、证据规则与实验](https://arxiv.org/html/2610.40578v1) · [VeriCUA：摘要与提交记录](https://arxiv.org/abs/2610.40578v1)

## 开源项目

### 3. nesformer 将 NES CPU 编译进 Qwen 架构权重：无需训练，画面和控制仍由宿主程序处理

开发者 Drew Breunig 发布 nesformer，把 NES 的 6502 CPU、工作内存与程序 ROM 运行逻辑编译成 Qwen3.5 架构检查点。所有权重由编译器计算，模型逐 token 输出 CPU 执行记录，并非通过游戏样本训练学会模拟。宿主程序负责绘图、手柄和时序等外围功能。项目是确定性计算的演示，作者称整体仍比真实主机慢 150–290 倍。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-31/3.svg" | relative_url }}" alt="nesformer 的模型与宿主分工。编译器生成检查点 → 模型逐 token 执行 CPU → 宿主处理外围功能" loading="lazy"></figure>

- 检查点为约 466.6M 参数、BF16 权重约 933 MB，其中约 9.3M 参数非零；压缩包约 3.3 MB 不等于运行内存需求。模型使用七层 Gated DeltaNet 加一层全零注意力。
- DeltaNet 状态存放 CPU 寄存器、2 KB RAM 与 32 KB 程序 ROM；PPU 画面、控制器、垂直消隐时序和 I/O 返回由宿主提供，音频未实现。
- 支持 NROM、iNES mapper 0、151 条官方操作码；非官方操作码、从 RAM 执行代码或其他 mapper 均受限制，不能称兼容全部 NES 游戏。
- 作者报告，stock Transformers 在 CPU/BF16 下核对 2651 个位置无差异；更长游戏记录和逐帧比较采用其他运行路径，不把不同验证范围合并成全程原生框架验证。
- 默认 numba 引擎会跳过全零块与可识别的空转等待；作者单核约 1650 token/s、stock Transformers 约 10 token/s，硬件条件与优化路径不同，不能将前者写成通用 Qwen 推理速度。
- 代码为 MIT，附带测试 ROM 各保留自身许可，其他游戏需用户自行提供。本期只读仓库和发布记录，未下载权重或游戏、未运行模拟。

**为什么值得关注：** 这个项目展示了如何把已知算法映射成模型架构可执行的状态机。它不能证明普通语言模型自动获得了可靠 CPU 模拟能力，也不是高效替代传统模拟器的方案。

来源：[nesformer：实现边界、验证与速度说明](https://github.com/dbreunig/nesformer)

### 5. NVIDIA 展示本地语音投影案例：现场生成回复中位等待 1.70 秒，缓存录音为 0.72 秒

NVIDIA 员工用 Nemotron Voice Agent 搭建 MonsterHouse，将语音识别、Bolt E4B 对话、Magpie TTS 与 Audio2Face-3D 接到投影角色。作者报告，从说话结束到开始出声，现场生成路径中位数为 1.70 秒，缓存回复为 0.72 秒。两条路径执行的工作不同，不能把差值归因于单个模型优化。完整 MonsterHouse 代码尚未打包发布，文章提供的是案例和可用组件入口。

## 行业动态

### 6. Google 计划 2027 年支持共享训练偏好信号：robots.txt 保留 Google-Extended 单独控制

Google 宣布计划支持 robots.txt 中跨厂商共享的 AI 训练偏好信号，目标在 2027 年与其他参与者一起落地。方案基于 IETF AIPREF 工作组的训练定义，仍在推进标准化。网站可表达共同偏好，同时保留各厂商单独规则。今天公布的是支持计划，不能当成已经全面生效的抓取或训练阻断机制。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-31/6.svg" | relative_url }}" alt="Google 计划如何解释共享训练信号。先核对专用控制 → 未指定时解释共享偏好 → 2027 年计划支持" loading="lazy"></figure>

- 按计划，网站用共享 policy token 选择不用于训练，且未明确配置 Google-Extended 时，Google 将按禁止 Google-Extended 处理。
- 现有 Google-Extended 等专用控制继续工作，网站可在共同选择之外为具体厂商设置不同规则；不能仅写共享规则而忽略已有显式设置。
- 官方称允许 Google-Extended 的网站有资格通过 Gemini Apps 的 grounding 出现在回答中并获得点击；有资格不等于保证展示或流量。
- AIPREF 其余词汇仍在多方讨论，Google 未在本文给出可直接照抄的最终 policy token 语法；本期不编造 robots.txt 配置范例。
- 偏好信号依赖参与者解释和采用，不是网络访问控制，也不证明历史训练数据会被删除。具体实施与支持进展仍待后续更新。

**为什么值得关注：** 站点维护者可以先盘点现有厂商专用规则，待最终语法和生效时间明确后再验证。共同偏好减少配置负担的潜力，应与实际采用范围分开看。
