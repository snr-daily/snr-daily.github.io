## 模型发布

### 1. 微软发布 Microsoft-Decision-1：给 Agent 做快速裁决，P50 延迟约为 GPT-6 Sol 的 1/35

微软 10 月 9 日推出决策模型 Microsoft-Decision-1，已在 Microsoft Foundry 和 OpenRouter 上线。它不生成文本，而是在调用方给定的一组选项上，一次前向就给出每个选项的校准概率，支持是否题、多选、评分和按评分标准给 AI 回答或 Agent 动作打分，定位是路由、分类、优先级排序、校验和工作流控制。模型由 Qwen3.5-9B 后训练而来，微软说之后会改用 MAI 和 OpenAI 的模型做底座。这是继本周 OpenAI Decisions API 和多款开源决策模型之后，又一家大厂进入“决策模型”这一新品类。

- 价格为每百万输入 token 0.042 美元，输出 token 免费；在 OpenRouter 上走专门的 Decisions API，不兼容普通的 chat completions SDK。
- 微软称在 36 个基准、近 15 万道训练时未见过的题目上准确率最高；速度是第二名 Quyet-1.0-Large 的 4.5 倍、GPT-6 Sol 的约 35 倍（P50 延迟）。
- 稳健性测试把同一请求做 8 种等价改写，平均只有 1.3% 的情况会改变决定；改写选项描述、倒序或打乱选项时一次都没变。安全测试覆盖 11 个基准的 5250 条有害内容、越狱和提示词注入请求。
- 内部用例里，Xbox 研究团队用它把 1 万多条玩家反馈归到固定主题，质量与 GPT-6 Sol 相当，速度快 14 倍以上、成本低 200 倍。以上均为微软自测数据。

**为什么值得关注：** Agent 每一步“继续还是停、交给谁”的判断都要花时间和钱，20 个串行决定每个多 100 毫秒，整条流程就多 2 秒。专用决策模型把这类判断压到极低延迟和成本，但用它当安全闸门前要看下一条的研究。

来源：[Microsoft Command Line 博客](https://commandline.microsoft.com/microsoft-decision-1-model-foundry/) · [OpenRouter 模型页](https://openrouter.ai/microsoft/microsoft-decision-1)

## 研究

### 2. 论文：把决策模型当 Agent 安全闸门，改一个选项名就能让放行率升到 93%–100%

南加州大学的研究者 10 月 8 日发布论文，专门测试“类型化决策模型”在 Agent 系统里当安全闸门的表现，也就是读一个拟执行的工具调用或外来消息，判断放行还是拦截。他们测了五个基于 ModernBERT、GLiClass 等编码器的开源决策模型，以 Qwen2.5-Instruct 两个尺寸作对照，并把“该拦没拦”（fail-open，属于漏洞）和“不该拦却拦了”（fail-closed，只是成本）分开统计。结论很直接：这些模型能减少需要人工复核的量，但不应该是最终做决定的那一环。

- 在提示词注入、越狱、有害内容筛查上，放行与拦截判断的准确率只有 36% 到 72%，随机猜是 50%；某个方向错误率低，往往只是模型默认偏向放行或偏向拦截。
- 在作者构建的 GuardBench 工具调用测试里，往输入里加 6 行与策略无关的普通服务器日志，就能让一个原本判对的闸门 fail-open 率从 0% 升到 63%。
- 所谓“选项通道攻击”不改被判断的文本，只给“放行”选项起一个误导性的名字，就能让把选项名放进输入的 4 个模型 fail-open 率升到 93% 到 100%。
- 作者测试的所有防御都被攻破；把最没把握的判断升级给人也没用，因为被攻击翻转的决定和原来一样自信。把策略字段解析成类型化值能挡住一种攻击，但这时一条确定性规则就能在 6 条策略上做到 100% 准确，模型反而多余。代码已在 GitHub 公开。

**为什么值得关注：** 测的是小型编码器模型，不是上一条的 Microsoft-Decision-1，但问题出在“让模型读攻击者可控的文本再做安全决定”这一结构上。如果打算用决策模型做权限闸门，选项名和策略应当写在代码里，而不是从配置或外部数据拼进来，最终放行仍要靠确定性规则或人工。

来源：[arXiv 论文](https://arxiv.org/abs/2610.12292) · [代码仓库](https://github.com/ArminAzizi98/option-channel-attack)

### 3. Claude Science 补全第一张全天紫外星图：没人观测过的三分之一天空由模型推算

约翰斯·霍普金斯大学天体物理学家、Anthropic 研究员 Brice Ménard 10 月 8 日介绍了他用 Claude Science 做出的第一张完整的全天紫外星图。紫外线被臭氧层吸收，只能从太空观测，而观测最多的 NASA GALEX 任务为保护探测器刻意避开了亮星密集的银河盘面，因此一直没有完整的紫外天图。这类工作要逐像素校准、反复分析，耗时数周，天文学家通常一拖再拖。这次由 Claude 调度一组 Agent 完成数据搜集、校准、拼接和补洞，Ménard 主要负责给方向和验收。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-10/3.svg" | relative_url }}" alt="全天紫外星图的制作流程。搜集公开巡天数据 → 各巡天内部校准 → 交叉定标与拼接 → 推算未观测的三分之一 → 叠加恒星并迭代" loading="lazy"></figure>

- 数据来自 GALEX、Swift、韩国 FIMS/SPEAR、欧洲 TD-1 等任务；GALEX 在 2003 到 2013 年间拍了约 3.8 万次观测，覆盖约三分之二的天空。
- 剩下约三分之一从未有紫外观测的天空，用 Claude 从已有区域学到的“紫外亮度与可见光、红外、射电的关系”来推算；故意遮住已知区域做检验，预测与实测的差距约在 10% 以内。成图逐像素标注“实测”或“推算”并附不确定度。
- 最后叠加了根据欧空局 Gaia 可见光数据推算的 1 亿多颗恒星的紫外亮度。
- 过程并非一次成功。Ménard 在暗场里发现一圈圈 GALEX 视场的印子，原因是大气辉光没扣干净，这个问题 Claude 一开始就列为已知风险，却通过了其他 Agent 的两轮审查；指出后，Claude 对 3.8 万次观测全部重做校正，几小时后消除。

**为什么值得关注：** 这类“大家都需要、没人有空做”的数据整理工作，正是多 Agent 科研工具最先落地的地方。但案例也说明 Agent 互审会漏掉肉眼一看就有的问题，领域专家的最终把关仍不可少；推算区域的数据只适合教学和参考，不能当实测用。

来源：[Anthropic](https://www.anthropic.com/research/the-missing-map-of-the-sky) · [The Decoder](https://the-decoder.com/anthropics-claude-science-creates-the-first-complete-ultraviolet-map-of-the-sky/)

### 4. FAR.AI 论文：探针读模型内部激活抓 Agent 暗中破坏，AUC 98.8%，超过 Opus 5.5 文本监控

AI 安全机构 FAR.AI 的研究者 10 月 8 日发布论文，尝试把“白盒探针”做成可用于前沿 Agent 的监控手段。探针是读取模型内部激活来判断它是否在说谎或搞破坏的小分类器，传统做法只能识别较窄的欺骗类型。作者整理了他们称为迄今最大的欺骗数据集 FIBS 来训练探针，并设计了能汇总多层、多个 token 信息的新探针结构。在 SHADE-Arena 这类多步骤、带工具调用的 Agent 任务里，探针识别暗中执行的恶意动作的效果超过了用 Opus 5.5 读文本做监控的基线。

- 在 SHADE-Arena 上，探针的 AUC 达到 98.8%；在 Qwen3.5-397B-A17B 上测的 14 个场景中，四种探针都高于 Opus 5.5 文本监控和模型自我监控，且底层模型越大效果越好。
- 作者还测了“内省式欺骗”，即光看上下文无法判断真假、只能靠诱导或了解训练数据才能确认的情况；其中一项实验里，探针区分模型真实隐藏目标与其他目标的 AUC 最高 99.7%。
- 探针也能识别开源模型在政治敏感话题上说谎，以及在压力下谎报自身信念。
- 已知局限是 FIBS 中只有 5.5% 的样本含推理过程，且对绝大多数被测模型来说是非本模型生成的数据。数据集已公开。

**为什么值得关注：** 最近几起 Agent 失控事件都暴露了一个问题，只看模型输出的文本很难发现它在暗中做别的事。探针需要能读模型内部激活，只适用于开源权重模型或模型厂商自己部署，但它给监控提供了一条不依赖模型“说实话”的路径。

来源：[arXiv 论文](https://arxiv.org/abs/2610.12445) · [FAR.AI 关于白盒检测欺骗的立场文章](https://www.far.ai/blog/ai-deception-white-box)

### 5. 论文重估 METR 时间跨度：从 3 分钟到 30 分钟，比从 30 分钟到 5 小时容易得多

METR 的“50% 时间跨度”指 AI 有一半把握完成的软件任务、人类需要花多长时间，已成为衡量模型进展最常被引用的曲线之一。加州大学伯克利分校统计学者 Drew T. Nguyen 和 William Fithian 10 月 8 日发布论文，用样条和项目反应理论重新拟合这条曲线。原方法假设任务对 AI 的难度与人类用时的对数成线性关系，他们放宽了这一假设，发现实际关系并不均匀。

- 数据覆盖 228 个任务、26 个 AI 系统。
- 拟合出的样条可理解为把“人类用时”换算成“对 AI 的难度”的函数，它在 2 到 30 分钟之间几乎是平的，在其他区间接近线性。
- 这意味着同样是 10 倍增长，时间跨度从 3 分钟到 30 分钟要比从 30 分钟到 5 小时容易得多，直接按倍数外推会失真。
- 作者给出的新点估计在交叉验证的多种评分规则下表现更好，并提供检验构念效度的诊断图，建议今后发布时间跨度时与诊断图一起看。

**为什么值得关注：** 很多关于“AI 能力每几个月翻倍”的判断都建立在这条曲线上。这篇论文提示，短任务区间的快速增长不能简单外推到小时级任务，引用时间跨度做规划或预测时要看清口径。

来源：[arXiv 论文](https://arxiv.org/abs/2610.12466)

### 6. Ai2 公开 GPU 集群调度改造：按预算分配算力，调试任务 p90 排队从 2 小时降到 30 秒

艾伦人工智能研究所（Ai2）基础设施团队 10 月 9 日介绍了他们为数千块 H100、B200、B300 重写调度器的经验。Ai2 约 150 名研究人员申请的 GPU 一直是可用量的 2 到 3 倍，旧的优先级调度导致了占卡不用、人人都标高优先级、值班工程师大量时间花在和不可抢占任务的主人协商上。新系统改为由管理者按研究方向分配 GPU 时间预算，配合按项目树分层的公平份额调度，以及一份“调度契约”。他们说这把“每个项目该分多少卡”从临时的运维谈判变成了透明的预算流程。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-10/6.svg" | relative_url }}" alt="最大 H100 集群的排队等待中位数。旧的优先级调度 5 分钟；新的预算加公平份额调度 24 秒" loading="lazy"></figure>

<details class="snr-data"><summary>查看数据</summary><table><thead><tr><th>项目</th><th>条形长度按秒计，越短越好</th></tr></thead><tbody><tr><td>旧的优先级调度</td><td>5 分钟</td></tr><tr><td>新的预算加公平份额调度</td><td>24 秒</td></tr></tbody></table></details>

- 调度契约要求每个任务声明最短运行时间（上限 8 小时），这段时间内不被抢占并计入预算；之后调度器可以抢占并自动重新排队。最短运行时间设为 0 的任务不计预算，但随时可被抢占。
- 公平份额按 7 天滑动窗口计算，实际占用低于分配的组排在前面。上线前用模拟器回放历史和构造场景，调整窗口长度等参数。
- 30 天测试期内各团队拿到了应得 GPU 时数的 98%，15 个团队中 13 个达到 95% 以上，最差的 90%；集群占用率前后都保持在 98%，交付时间中有 18% 来自不计预算的空闲算力。
- 调试任务的 p90 排队时间从 2 小时降到 30 秒；最大的 H100 集群排队中位数从 5 分钟降到 24 秒；坏节点能在任务跑满最短时间后自动腾空，需要人工介入的维修减少 74%。

**为什么值得关注：** 算力紧张的团队普遍遇到“抢卡、占卡、优先级通胀”，Ai2 的经验是让每一种钻空子的手段都花自己的预算。分层公平份额本身不新，SLURM 和 YARN 里都有，值得借鉴的是“最短运行时间换不被抢占”这份契约和上线前先做模拟。

来源：[Ai2 / Hugging Face 博客](https://huggingface.co/blog/allenai/impactful-scheduling)

## 开发工具

### 7. Claude Managed Agents 开放动态工作流公测：Agent 自己写编排程序，一次运行最多调度 1000 个子 Agent

Anthropic 10 月 9 日在 Claude Managed Agents 中开放动态工作流（dynamic workflows）公测。开启后，Agent 遇到可拆成很多小块的任务，比如审阅几百份文档、交叉核对大量来源，可以自己写一个“工作流”程序，让许多 Agent 分阶段并行处理，再把结果汇总。这个程序由服务器在后台作为一次 workflow run 执行，主 Agent 可以继续干别的或结束本轮。它此前只在 Claude Code 里提供，现在搬到了托管的服务端，开发者可以直接嵌进自己的产品。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-10/7.svg" | relative_url }}" alt="一次 workflow run 是怎么跑起来的。Agent 判断要开运行 → 服务器后台执行 → 分阶段扇出 → 汇总结果 → 主 Agent 读取结果" loading="lazy"></figure>

- 开启方式是在 Agent 定义的 multiagent 字段里用 multiagent_20261001 类型并启用 workflows，请求带 managed-agents-2026-04-01 beta 头；进度通过会话事件流里的 workflow_run.* 事件跟踪，每个子 Agent 的线程都能单独查看。
- 官方文档列出的限制是一次运行同时最多 64 个线程在工作，整个运行期间累计最多启动 1000 个 Agent，默认寿命 24 小时，一个会话默认最多同时开 10 个运行。部分报道写成“1000 个并行”，与文档不符。
- 运行本身不单独计价，各子 Agent 的 token 按各自模型费率计费，并计入会话预算；到达预算时所有运行暂停，提高或取消预算后继续。文档建议用系统提示词告诉 Agent 什么时候才值得开运行。
- 据 The Decoder 援引 Anthropic 的测试，在一个 11.6 万行、埋了 70 个 bug 的代码库里，单个 Agent 每次找到 14 到 27 个，动态工作流稳定找到 66 个。

**为什么值得关注：** 这把“一个任务拆给几百个 Agent”从本地 CLI 能力变成了可以直接调用的托管 API，适合审计、迁移、批量审阅这类工作。代价是 token 消耗会成倍增长，上线前务必设好会话预算，并用自己的任务实测收益。

来源：[Claude Platform 发布说明](https://platform.claude.com/docs/en/release-notes/overview) · [Workflow runs 文档](https://platform.claude.com/docs/en/managed-agents/workflow-runs) · [The Decoder](https://the-decoder.com/anthropics-claude-can-now-orchestrate-up-to-1000-ai-agents-in-parallel-through-dynamic-workflows/)

### 8. GitHub Copilot 支持本地模型和系统级沙箱：微软量化版 MAI Code 1.1 Flash 在笔记本上跑出 70.8% SWE-Bench

GitHub 和 Windows 团队 10 月 7 日公布 Copilot 的两项本地化能力。一是本地模型，Copilot CLI、Copilot 应用和 VS Code 可以直接选本地模型，月底前还会上线 Auto 模式，自动决定每一步用本地还是云端推理。二是本地沙箱正式可用，Agent 跑的命令被限制在开发者或企业设定的文件、网络、凭据权限内。为此微软 AI 做了 MAI Code 1.1 Flash 的本地版，这是一个 1370 亿总参数、68 亿激活参数的编码 MoE 模型，量化后可在 NVIDIA RTX Spark 的 Surface Laptop Ultra 上运行。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-10/8.svg" | relative_url }}" alt="SWE-Bench Verified 得分。MAI Code 1.1 Flash 云端原版 72.6%；MAI Code 1.1 Flash 本地量化版 70.8%；GPT-OSS-120B（GGUF） 32.0%" loading="lazy"></figure>

- 本地版用约 3.3 bit/权重的混合精度量化加投机解码，体积 53 GB，比云端 BF16 版小 80%；256k 上下文时峰值内存 75.5 GB，64k 和 128k 上下文的提示词处理速度分别为每秒 923.5 和 769.8 个 token。
- 微软 10 月 5 日的测试中，量化版 SWE-Bench Verified 为 70.80%（云端原版 72.6%），Terminal-Bench 2.1 为 66.29%（原版 62.9%）；作为对照的 GPT-OSS-120B GGUF 分别为 32.0% 和 23.6%。
- Copilot CLI 从 1.0.94-0 起，可在 /model 里发现本机运行的 Ollama 模型，模型须支持工具调用和流式输出。GitHub 特别提醒，选本地模型不等于离线，也不会关闭遥测，离线需显式设置 COPILOT_OFFLINE=true。
- 沙箱由开源库 Microsoft eXecution Container（MXC）实现，把同一份策略翻译成各系统的原生机制，Windows 用 BaseContainer，macOS 用 Seatbelt，Linux 用 bubblewrap；企业可强制开启且不允许开发者放宽，不额外收费。

**为什么值得关注：** 编码 Agent 正在把“模型在哪跑”和“命令能碰什么”拆成两个独立的开关，前者影响成本和隐私，后者决定出事时的影响面。对企业来说，强制沙箱策略比换本地模型更值得先落地；本地模型则要注意 70 多 GB 的内存门槛。
