### 1. REA 6.7.0 修正 MCP 配置重复键处理，并整合新静态分析能力

REA 10 月 18 日发布 rea-agents 6.7.0，修正安装和卸载时对重复 JSON／JSONC 成员的处理。新版编辑客户端实际读取的最后一个同名成员，并拒绝会重新激活被遮蔽旧配置的删除操作。此版本同时包含同日 6.6.0 的静态分析、证据保留和迁移改动；6.6.0 虽有标签，但未发布到 npm。涉及旧证据文件的用户需要阅读破坏性变更，不能仅按补丁升级理解。

- 新增调用方安装的 Kuna 静态分析提供方，支持过程、伪代码、汇编、调用关系和缓存字符串查询；已记录验证为 Linux 上 Kuna 1.833，不支持 Windows、PE 和通用 Mach-O。
- 可复用已完成分析来查询选定 JavaScript 事实，并在一次 APK 解码中请求多个语言资源表，各自保留状态与覆盖说明。
- Ghidra 的 Windows ARM PE 支持限定在 Windows x64 主机环境；不能外推为已验证 Windows-on-Arm 主机或 ARM64EC／ARM64X。
- Evidence 和分析快照新增明确覆盖字段，旧文件不自动迁移，需要重新生成；取消、失败和清理阶段会保留已完成观察及原始原因。

**为什么值得关注：** 重复配置键可能让编辑器看到的内容与客户端实际读取值不同，修复有助于减少安装和卸载的隐性行为变化。分析能力和证据格式也有迁移范围，应按实际主机、目标格式与历史文件分别检查。

### 2. neurastheniacc 用本地 Qwen 编译受限 C：通过 WAT 校验和 Clang 对照验收

实验项目 neurastheniacc 用本地 Qwen 把受限 C 函数翻译为 WebAssembly 文本 WAT，再用常规工具生成 Wasm。生成无效 WAT 时，执行框架把解析反馈送回模型重试，默认最多三次。基准还将产物与 Clang 编译的原程序作随机输入输出对照，区分语法合法和行为一致。作者把它定位为可执行实验，本期依据社区线索关注，不将其描述为通用 C 编译器。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-19/2.svg" | relative_url }}" alt="实验如何检查模型生成的编译结果。限制输入语法 → 本地模型生成 WAT → 基准比较程序行为" loading="lazy"></figure>

- 输入仅支持一个返回 uint32_t、且恰有两个 uint32_t 参数的函数；支持局部变量、位运算和部分条件分支，不支持指针、数组、循环、递归或函数调用。
- 仓库基准为 32 个样例，其中 8 个固定、24 个生成。Qwen3.5-4B 关闭思考通过 23 个，开启思考通过 7 个；后者有 25 个触及 token 限制。
- Qwen3.8-27B 关闭思考通过 31/32，运行 4 分 39 秒；开启思考为 32/32，运行 43 分 11 秒。这是项目方小样本测试，不是通用编译正确率。
- 上述测试均为 Apple Silicon Metal、贪心解码并将重试参数设为 5；思考开关两组的上下文和输出预算不同，不能把差异只归因于思考能力。
- 默认模型首次下载约 2.75 GB，推理在本地完成；项目目前仅报告 macOS Apple Silicon 测试，Linux 性能与兼容性未获相同验证。代码采用 MIT 许可。

**为什么值得关注：** 这个实验展示了生成器、解析器反馈和独立行为对照各自的作用。编译成功不等于语义正确，有限随机测试也不能代替对完整语言和所有输入的证明。

来源：[neurastheniacc：支持语法、重试机制和基准条件](https://github.com/vivshaw/neurastheniacc)

### 3. trustbut 复跑改动前后的测试：检查新增测试是否真正证明了改动

trustbut 是面向 AI 编程与人工提交的本地核验工具：它先复跑当前代码的测试，再把新增或修改的测试放到改动前代码上运行。如果测试在两边都通过，就不能据此证明新增行为；工具还会标记跳过测试、删除断言和屏蔽类型检查等变化。它依赖 Git 与项目自己的测试运行器，不使用 LLM。本期依据过去两天的社区线索和当前官方仓库介绍其功能，不推断项目刚刚首次发布。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-19/3.svg" | relative_url }}" alt="trustbut 如何核对测试与代码改动。复跑当前测试 → 对照改动前代码 → 生成核验报告" loading="lazy"></figure>

- 当前说明列出 11 种语言，并支持能输出 JUnit XML 的其他运行器；需要 Node.js 22 或以上，以及项目自己的依赖和工具链。
- 输出为 PASS、WARN、FAIL 核验报告，可用版本化 JSON 格式记录发现。测试在临时工作区中运行，主工作目录不会被改写。
- 作者以 0.7.0 检查了 201 个已合并 PR，其中 Agent 组成功运行 53/103 个，人类组 56/98 个；大量无法运行的案例涉及依赖、工具链或运行器限制。
- 成功运行的子样本中，Agent 的 283 项新增或修改测试有 275 项在旧代码上失败，人类为 294/333；这不是全部生成代码的可靠率，也不证明合并前没有问题。
- 旧代码缺少新接口时，测试可能根本无法运行，报告会单独标记；核验报告不替代代码审阅，扫描到的跳过或屏蔽也不自动意味着恶意。

**为什么值得关注：** 比“测试全部通过”更有用的问题是：哪个测试能区分改动前后的行为。使用这种核验前，仍要确认测试环境可信、依赖完整，以及失败来自行为差异还是环境差异。

来源：[trustbut：方法、运行条件与试点结果](https://github.com/isAlmogK/trustbut)

### 4. Sphinx 在 Git 推送前提问：让开发者解释 AI 代码的失败场景

Sphinx 把代码理解检查接入 Git：推送到受保护分支时暂停操作，由独立评审模型阅读已提交差异，再要求开发者预测代码行为。回答有误时，工具解释原因并换一个场景继续提问，通过后恢复原来的推送。问题围绕重试、并发和不变量等实际行为，评审模型不读取生成代码时的聊天。本期核实的是当前项目功能与社区展示，尚无证据证明它能改善任意团队的缺陷率。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-19/4.svg" | relative_url }}" alt="Sphinx 的代码理解检查。受保护分支推送 → 回答行为问题 → 恢复或暂停推送" loading="lazy"></figure>

- 需要 Node.js 22.19 或以上，支持 macOS、Linux、WSL；安装会设置全局 Git hooksPath，默认检查 main 和 master，并尝试先串联已有 hooks。
- 可使用已登录的编程 CLI、OpenRouter 或兼容端点作为评审后端；所选提供方会接收差异、相关代码、回答和项目背景，因此数据边界取决于后端。
- Git 等待上限为 25 分钟，允许暂停或跳过；同一变更的通过记录默认有效 24 小时，但代码、目标或策略变化会触发重新检查。
- 默认未限制模型调用次数，常见检查约 5–8 次请求再加回答轮次；可配置上限。评审模型可能判断错误，项目也明确它是理解练习，不是不可绕过的安全关卡。
- 当前 0.1 版本只覆盖本地提交和推送，不覆盖网页合并、CI 必需检查或部署，也不能读取二进制内容。

**为什么值得关注：** 这种提问可以把人工审阅从“看过差异”推进到“解释失败时会发生什么”。团队试用时应明确代码可送往哪个评审后端，以及 hooks 对已有 Git 工作流的影响。

来源：[Sphinx：官方功能展示](https://sphinx-six-theta.vercel.app/) · [Sphinx：配置、成本与能力边界](https://github.com/parthh01/sphinx)

### 5. LLM 插件更新：Datasette 补齐 httpx 依赖，echo 完善模拟 token 统计

Simon Willison 10 月 18 日发布 llm-tools-datasette 0.1.1 与 llm-echo 0.5。前者修复 LLM 0.33 切换到 httpx2 后暴露的隐式依赖问题，让 Datasette 数据库继续作为工具接入。后者是调试用的回显模型，不运行真实 LLM，本次把工具调用、系统提示和推理片段纳入模拟 token 统计。两项更新分别针对集成可用性和测试可观测性，不代表模型推理能力变化。

- Datasette 插件安装在 LLM 所在环境，工具参数指向具体数据库 URL，可通过调试详情观察调用；README 也给出 Python API 接入方式。
- llm-echo 将收到的提示、系统消息、附件等结构作为 JSON 返回，可用预设推理片段检查流式推理处理。
- echo 还能用指定工具调用构造测试，并检查工具结果是否进入后续响应；其计数是测试模拟，不能当作任何真实供应商的计费结果。
- 这两个插件仓库均采用 Apache 2.0 许可；本期阅读发布说明与用法，没有调用付费模型或接入实际数据库。

**为什么值得关注：** 插件应显式声明自己使用的依赖，避免依赖主程序碰巧携带某个库。回显后端则适合先检查提示、工具结果和流式事件是否按预期传递，再做真实模型验收。
