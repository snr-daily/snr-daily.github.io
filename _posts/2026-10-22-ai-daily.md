## 模型发布

### 1. IBM 更新 Granite Speech：新增 2B 语音模型，改善转写、翻译与说话人归属

IBM 10 月 21 日发布 Granite Speech 5.0 2B，并更新 470M Turbo CTC 与 4.1 2B Plus。三条路线分别面向高准确率转写与翻译、快速转写，以及多说话人长录音。5.0 2B 支持六种语言转写，并支持相应语言与英语互译，另有英语到意大利语和普通话翻译。普通话在这里是翻译目标，不能据此宣称已经支持中文语音转写。

- 5.0 2B 的转写语言是英语、法语、德语、西班牙语、葡萄牙语和日语；关键词偏置列表上限为 2000 项。
- 三个模型均采用 Apache 2.0，原生支持 Transformers；5.0 2B 发布说明还列出 vLLM、llama.cpp 与 Apple Silicon 的 mlx-audio。
- 4.1 2B Plus 的长录音词错误率 WER 从 13.53 降至 10.22，约下降 24%；说话人归属指标 WDER 则从 4.40 降至 4.10，不能混作同一降幅。
- Turbo CTC 新增多语言、标点和大小写，官方 Open ASR 榜单 RTFx 从约 12600 到 19870；批处理吞吐指标不等于单请求流式延迟。

**为什么值得关注：** 按转写、翻译和说话人归属分别选模型，比只按参数量更有用。业务上线前应使用真实口音、噪声与长录音复测，本期未运行模型。

来源：[IBM：Granite Speech 5.0 发布与指标表](https://huggingface.co/blog/ibm-granite/granite-speech-5)

### 2. NVIDIA 更新 Nemotron 检索模型：覆盖图文嵌入、重排与 631M 文档解析

NVIDIA 10 月 21 日扩展 Nemotron Retriever，发布 8B 与 1B 图文嵌入、8B 重排及 631M Parse。Parse 将文档图片转换为带阅读顺序、表格和图表结构的内容，再由嵌入与重排为 Agent 选择证据。厂商固定 Agent 和任务、只改变检索配置的实验中，增加重排使两种嵌入配置的 Agent token 消耗约下降 14% 和 13%。这不等于总服务账单下降相同比例，重排自身的成本还需计算。

<details class="snr-data"><summary>查看数据</summary><table><thead><tr><th>项目</th><th>单张 H100，页/秒；标签附 ParseBench 分数</th></tr></thead><tbody><tr><td>单遍 · 分数 72.74</td><td>16.1</td></tr><tr><td>双遍 · 分数 74.92</td><td>11.2</td></tr><tr><td>三遍 · 分数 75.20</td><td>10.5</td></tr></tbody></table></details>

- 1B 嵌入提供 BF16 与 NVFP4，后者同时量化文字和图像编码器；部署收益取决于支持的硬件。
- Parse 在单张 H100 上，单遍、双遍、三遍分别为 16.1、11.2、10.5 页/秒，对应 ParseBench 为 72.74、74.92、75.20；不是三种不同模型。
- 增加遍数会针对表格和图表区域再处理，以吞吐换取解析质量；ParseBench 分数不应直接换算为百分比准确率。
- 嵌入模型训练冻结了语言组件，官方预期纯文本嵌入可沿用上一代索引；实际升级仍应核对版本、向量和检索回归。

**为什么值得关注：** 文档 Agent 可以把解析、召回、重排分别验收，并把证据质量和完整成本一起记录。更少的 Agent token 是一个观测量，不能替代端到端成本测试。

来源：[NVIDIA：Nemotron 3.5 检索与 Parse 发布说明](https://huggingface.co/blog/nvidia/nemotron-retriever-world-class-agentic-retrieval)

### 3. NVIDIA 发布 Kumo Relational：用历史样本在多张关联表上直接预测

NVIDIA 10 月 21 日介绍 Kumo Relational，以预训练关系模型对流失、需求等任务做上下文预测。它保留表间键关系和时间信息，无需为每个新任务先训练一套监督模型或手工展平所有表。推理最多使用 10000 个带目标的历史样本，因此“无需任务训练”不等于不需要历史数据。发布包括 GPU 原生库、模型权重和 NIM 部署路径。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-22/3.svg" | relative_url }}" alt="Kumo Relational 如何形成预测。定义预测查询 → 构造历史上下文 → 关系模型前向预测" loading="lazy"></figure>

- 官方评测覆盖 15 个数据库、41 项任务；不同数据集的 AUROC、MRR 与误差指标不合并成通用准确率。
- 时间任务按历史锚点生成上下文，预测时仅提供锚点以前的信息，目标从之后事件计算；实际数据管线仍需独立检查时间泄漏。
- 代码许可为 Apache 2.0，权重为 OpenMDW 1.1，两者应分别核对；模型卡提供 CUDA 推理示例。
- 作者提示，大训练集上专用监督模型仍可能更好，预测信号还须在有限图跳数内可达；必要时可微调。
- 论文链接编号为 2604.12596，本期报道 10 月的发布说明，不把论文首次出现时间改写为当天。

**为什么值得关注：** 多表预测可以先围绕明确业务目标构造小范围对照。验收重点包括历史标签、时间切分、图采样和现有模型基线，本期未导入企业数据测试。

来源：[NVIDIA：Kumo Relational 发布、评测与局限](https://huggingface.co/blog/nvidia/kumo-relational) · [NVIDIA：Kumo Relational 模型卡与许可](https://huggingface.co/nvidia/Kumo-Relational)

## 研究

### 4. Anthropic 用 Claude 检查攻击面：25 个项目中发现 493 项暴露与配置问题

Anthropic 10 月 20 日公布攻击面分析研究，检查不必要的默认暴露、过早可达代码和配置组合。团队在 25 个开源项目中报告 493 项问题，目标是让复杂代码在适当认证或配置检查之后才可达。这里的“问题”不等于 493 个可独立利用的漏洞。团队还报告与 OpenSSH 维护者合作，把算法许可检查前移，相关改动已进入 10.6。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-22/4.svg" | relative_url }}" alt="攻击面收缩如何验证。盘点入口与配置 → 动态追踪确认可达性 → 加控制并运行回归" loading="lazy"></figure>

- 研究覆盖超过 500 万行代码，盘点超过 17000 个配置项，其中 3842 个与安全控制或功能相关；这是研究样本规模，不是模型准确率。
- 162 组安全相关配置交互中，94 组会静默关闭安全控制，另外 68 组呈现不一致；需结合实际部署解释。
- 方法用动态执行轨迹核实可达性，并要求默认配置的修改通过项目测试与黑盒回归；会改变非默认行为的方案交给人工决定。
- 减少可达代码能限制未知缺陷的暴露，但并未删除或修好这些未知缺陷；研究技能仍在推进接入 OSS-Scanner。
- OpenSSH 10.6 已于 10 月 6 日发布，本条新闻是 20 日的分析方法与合作过程披露，不是新的 OpenSSH 版本发布。

**为什么值得关注：** 安全评审可同时检查检查顺序和配置交互，而不只搜索单个漏洞模式。改动仍需证明兼容性，避免把一份模型清单直接当作已验证修复。

### 5. Anthropic 推出 Claude Duet 研究预览：后台处理任务，敏感操作等待批准

Anthropic 10 月 21 日开放 Claude Duet 候补名单，先面向美国 Pro 与 Max 用户。它由 Opus 5.5 驱动，在云端虚拟机与浏览器中持续处理工作，不要求用户设备保持开机。相比等待用户打开聊天，Duet 会发送晨间简报，并在任务完成或需要决策时联系用户。研究预览与现有 Claude 共用用量，后台检查也计入限额。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-22/5.svg" | relative_url }}" alt="Claude Duet 如何处理后台工作。接收任务与上下文 → 后台准备并提交审批 → 执行后通知与交付" loading="lazy"></figure>

- 入口包括独立 iOS、Android 应用和 claude.ai；Team 与 Enterprise 暂不在预览范围。
- 可沿用账户记忆、技能与连接应用，通过一个持续线程接收文字或语音任务；官方称可接入超过 6000 个连接器和插件。
- 发送消息、付款、签署文件或删除前，会展示拟执行内容并等待批准；证券交易与账户间转账即使批准也不支持。
- 连接账户按每隔几小时检查，可能误判紧急程度或漏掉两次检查间的新消息；预览暂不能向用户展示浏览器。
- 使用 1Password 已存登录信息仍列为后续功能，不能写成首日已经开放。

**为什么值得关注：** 持续 Agent 的验收应覆盖后台用量、审批内容和实际执行结果。先从低风险、可复核任务试用，尤其检查它何时通知以及哪些动作需要确认。

### 6. GitHub 改为按引用串行写入：内部测试中不同分支吞吐提高 3–4 倍

GitHub 10 月 21 日介绍 Git 存储迁移的过渡设计，将写入协调从整个仓库缩小到单个 reference。不同分支的更新可并行，同一引用仍保持有序，减少跨区域往返对繁忙仓库的排队影响。团队称内部真实流量测试中，不同引用的写吞吐提高约 3–4 倍，延迟也下降。该结果针对其内部基础设施，不是所有用户推送立即提速的承诺。

- 当前多数仓库有 5 个副本，其中 2 个在 Azure；Azure 已承接约一半 Git 流量，迁移与后续架构仍在推进。
- 旧设计的整仓锁会把跨区域约 25ms 往返及多轮协调串行化；新设计主要减少不同引用之间的等待，不能消除网络延迟。
- 下一阶段让对象存储以虚拟副本加入写 quorum，再让读副本独立扩展；这属于逐步落地的架构路线。
- 文章指出虚拟读副本的后台对账最初只适合部分读负载，不能把设计方向写成所有读写路径都已完成迁移。

**为什么值得关注：** 大量 Agent 各写独立分支，会放大协调粒度的影响。这项工程实践说明可把真正需要排序的引用状态与对象、读取计算分开，但本地 Git 设置不因此自动改变。

### 7. PHP 修复两项严重漏洞：OpenAI 披露 AI 参与发现与补丁协调流程

PHP 团队 10 月 21 日发布 8.5.12、8.4.27、8.3.36 与 8.2.35，修复两项可能导致未认证远程代码执行的漏洞。OpenAI 同日介绍 Patch the Planet 的协作过程，称 Calif 使用 GPT-5.6 Sol 发现其中一项，Wiz 也独立发现并报告了两项。修复与发布由 PHP 维护者主导，合作方提前准备防护。对使用者而言，当前重点是部署官方或发行版修复，并确认服务进程实际运行了更新。

- PHP 公告列出的编号为 CVE-2026-109618 和 CVE-2026-109619；服务 Web 请求的 PHP 安装均在排查范围内，不能只检查某一种运行方式。
