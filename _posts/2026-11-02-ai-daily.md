## 研究

### 1. Jepsen 在 ParticleDB 测试中发现 96 项问题：新版本修复声明尚未获其复测

Jepsen 于 10 月 31 日公布对面向 AI 应用的多模型数据库 ParticleDB 的测试，覆盖 1.1.4 至 1.1.18.11.rc-22，共记录 96 项问题。大量异常在健康单节点、甚至单客户端条件下就能出现，包括查询结果错误、数据损坏和已提交写入丢失。到被测末版，除 10 项外的问题看起来已解决；Orkes 随后声称 1.1.19-rc.13 修复了报告中的剩余问题，但 Jepsen 没有评估这一后续版本。厂商当前下载页另列 10 月 30 日发布的 1.1.19-rc.16，不能把旧版发现直接说成当前版仍存在的 96 项缺陷。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-11-02/1.svg" | relative_url }}" alt="ParticleDB 报告的证据范围。测试旧版单节点 → 记录问题并追踪修复 → 区分后续修复声明" loading="lazy"></figure>

- 研究由 ParticleDB 开发商 Orkes 出资，遵循 Jepsen 伦理政策；报告只测试单节点，不评价企业版复制系统的正确性。
- 测试在 Debian 13 容器与 EC2 虚拟机上进行，包含随机读写、追加、事务内一致性，以及与 PostgreSQL 对照的随机 SQL 测试；另外模拟进程终止与存储故障。
- 96 项问题中，除 3 项外均在健康单节点上出现。末期默认 occ 模式仍在正常运行中丢失已提交写入；serializable 模式也有异常，不能只看设置名称判断保障。
- Jepsen 明确没有测试 1.1.18.11.rc-22 之后的版本。厂商当前页将早期被测构建列为不受支持的预发布版，并说明移除旧模式并不等于解决旧构建已经接受的行为问题。
- 报告讨论了 LLM 辅助开发与文档可信度，但这属于作者基于本项目经验的判断；该测试没有通过对照实验确定每个缺陷由模型生成代码造成。

**为什么值得关注：** 给 Agent 接入数据库之前，应固定版本和事务配置，用业务不变量与故障恢复测试核对实际行为。厂商的修复说明、旧版测试发现和新版本独立复测是三类不同证据，不能相互替代。

## 开源项目

### 2. Memdoor 公布 Qwen3.8-27B 协作编程实验：10 题各跑 5 轮，49 次通过隐藏测试

Memdoor 的 team-solve 工作流把规划、两路方案、编程、测试、复核与修复拆成独立上下文，通过磁盘文件交换材料。项目近期公布用 Qwen3.8-27B 经 OpenRouter 完成 LiveCodeBench Hard 列表前 10 题、每题 5 轮的结果：50 次运行中有 49 次通过全部隐藏测试。对照数据来自原方法作者的已有结果，其中 Fable 5 为每题单次调用，没有在这个工作流里重新运行。这个小样本说明流程值得复现，不能据此断言小模型在完整基准上全面超过大模型。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-11-02/2.svg" | relative_url }}" alt="team-solve 如何生成并检查程序。规划与并行提出方案 → 编程后运行公开样例 → 另以隐藏测试计分" loading="lazy"></figure>

- 五轮每轮通过题数依次为 10、10、10、10、9；同样 10 题的原作者 harness 均值为 9.6，Memdoor 为 9.8，项目自己也明确说差异处于噪声范围。
- 50 次已完成运行合计 35.79 美元、输出约 1530 万 token；单次模型运行时间中位数为 40 分钟，费用中位数为 0.39 美元。包含额外 16 次中断或修复尝试后费用为 38.77 美元，不能把中位数乘次数当总成本。
- 循环可见公开样例，最终分数依据隐藏测试；比赛题来自 2025 年春季，项目没有排除训练数据污染。调用经 OpenRouter 托管，不是本地 27B 模型实测。
- 工作记录说明原作者使用自有 FP8 vLLM，复现运行使用不同托管方，部分运行中途更换供应方；即使请求做过一致性核对，也不是完全相同的推理环境。
- 失败案例中，管理角色编造了错误反例，导致正确程序被改错；另有两次正确程序被覆盖后才恢复。项目提出的反例校验与保存版本改进，没有计入已发布分数。
- 仓库提供运行请求、回复、程序、评分与成本记录；本期仅核读资料，未执行工作流，也未独立复现分数。

**为什么值得关注：** 多角色协作的价值需要与调用次数、费用和耗时一起评估。对团队更有用的是可追踪的文件协作与独立测试机制，同时防止复核角色把已经正确的结果改坏。

### 3. agent-browser 0.41.1 修复 Cookie 参数被忽略：HttpOnly 与 SameSite 按设置写入

Vercel Labs 于 11 月 1 日发布 agent-browser 0.41.1，集中修复浏览器自动化中命令看似成功、结果却不符合要求的问题。相关合并记录说明，旧行为会忽略连字符形式的 Cookie 属性参数，即使命令报告成功，也可能没有写入 HttpOnly 或 SameSite。新版接受规范拼写并保留原有别名，设置单个 Cookie 时拒绝未知参数。发布说明还修复页面错误清空、MCP 选择器等待和敏感操作错误输出等行为。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-11-02/3.svg" | relative_url }}" alt="Cookie 设置修复针对什么问题。提交单个 Cookie 设置 → 校验参数并保留属性 → 核对实际存储状态" loading="lazy"></figure>

- cookies set 的 --http-only 与 --same-site 会实际生效；Cookie 修复合并记录同时说明未知参数检查针对单个 Cookie 写入，不应扩大成所有输入形式都采用同一检查。
- errors --clear 现在会移除已捕获的页面错误，便于分轮检查自动化任务，而不是保留上一轮错误造成误判。
- MCP 等待选择器时，裸整数选择器现在返回错误，不再被解释成按时长等待；这是错误输入的处理修复，不是增加新的定位方法。
- 插件对敏感操作的错误输出会省略不受支持的协议值；超出范围的空闲超时或无效输出限制会给出警告，避免溢出或静默忽略。
- 安装的 Agent skill 移除了未固定版本的 npx 执行权限；本期未安装或运行该工具，以上为官方发布与合并说明。

**为什么值得关注：** 网页任务的验收要检查实际 Cookie 属性、页面状态和错误记录。升级后的参数处理减少静默失败，但命令成功仍不能代替业务结果验证。

### 4. Copilot CLI 1.0.106-2 预发布修复 MCP 启动等待，并保留配置文件符号链接

GitHub 于 11 月 1 日发布 Copilot CLI 1.0.106-2 预发布版，主要处理 MCP 连接、配置保存和会话状态问题。对于接受连接却不回应的 HTTP MCP 服务，启动阶段现在只等待一次连接超时，不再重复等待三次。保存 MCP 修改时保留 mcp-config.json 的符号链接，并更新链接指向的文件。这个版本仍标为预发布，本期没有安装测试，也不把说明中的修复等同于所有连接故障均已解决。

- HTTP MCP 修复仅描述接受连接但从不响应的服务；官方没有承诺固定秒数，也不是将所有启动时间缩短三倍。
- /resume 会把已经在后台运行的会话切到前台，避免退出时把同一会话显示两次。
- /skills 的添加、移除与重新加载操作会与会话技能保持同步，刷新失败立即报告。
- 启用 --screen-reader 时，失败或被拒绝的工具调用、未知命令等错误以及警告会以 Error 或 Warning 前缀区分，避免朗读时与普通消息混淆。
- 配置保存修复涉及符号链接目标，不代表更改 MCP 服务本身的权限或可信边界；使用前仍需按自己的配置验证。

**为什么值得关注：** 依赖外置 MCP 服务和共享配置的团队，可以针对无响应服务、符号链接与后台会话恢复做升级验收。预发布版先核对这些具体行为，再决定是否进入常用环境。
