## 模型发布

### 1. Mistral Large 4 预览版上线：1 万亿总参数、490 亿激活，权重月底开放

法国 Mistral AI 10 月 6 日发布 Mistral Large 4（昵称 Le Chonk）的公开预览，这是一个原生多模态的 MoE 模型，总参数 1 万亿、激活 490 亿，是 Mistral 迄今最大的模型。目前只能通过 Mistral Studio 的 API 试用，Mistral 说正在与网络安全机构、审核过的合作方和政府部门做红队测试，权重计划在本月底开放。官方把它定位为美国和欧洲之外的开源权重强模型的替代，重点场景是编码、Agent、网络安全、金融和法律。据 Simon Willison 统计，它在 Artificial Analysis 综合指数上从去年 12 月 Mistral Large 3 的 9 分升到 38 分，他的评价是大约落后前沿 6 个月。

- 训练在 Mistral 自有的欧洲数据中心完成，用了 3,800 块 NVIDIA Grace Blackwell GPU，预览 API 也跑在同一套设施上；训练数据覆盖 160 多种语言，包括欧盟全部官方语言。
- API 定价为每百万输入 token 1.36 美元、输出 4.18 美元；据 Simon Willison 实测，API 只提供 none 和 high 两档推理强度。
- 官方成绩包括 DeepSWE v1.1 61.7%、SWE-Atlas-QnA 59.4%、Terminal-Bench 4 28.3%、AutomationBench 59.9%；Cybench 的 40 道题解出 93%。Simon Willison 指出，38 分略低于 5520 亿参数的 DeepSeek 4.1 Flash。
- Mistral 称在一项要求复现并修补真实开源漏洞的测试中，ML4 得分 82%，而部分闭源模型因为拒答几乎得零分；这正是它强调开源权重、可自行部署的理由。
- 后训练使用全异步强化学习，在约 3,000 块 GPU 上每天产出约 330 亿 token，其中约 160 亿是可训练的补全 token；Mistral 说这轮强化学习仍在进行，没有饱和迹象。
- 以上成绩均为 Mistral 自报，架构细节、更多基准和后训练方法要等权重发布时一并公开。

**为什么值得关注：** 需要自托管、对数据主权有要求的欧洲企业，以及做漏洞研究、经常被闭源模型拒答的安全团队，月底可能多一个 1 万亿级的开源选项。实际能否部署还要看许可证和硬件门槛，这两点 Mistral 尚未公布。

### 2. Google 发布 Nano Banana 2.1：图像生成质量提升，单张价格约为上一代一半

Google 10 月 6 日推出图像生成和对话式编辑模型 Nano Banana 2.1（API 名 gemini-nano-banana-2.1），接替 2 月发布的 Nano Banana 2（Gemini 3.1 Flash Image）。官方说它保持 Flash 级别的速度，在画质、提示词遵循、多轮对话中的角色一致性和文字渲染上都有明显改进，定位是 Nano Banana Pro 的高效版本。最直接的变化是价格，各分辨率单张图片的费用都降到上一代的一半左右。The Decoder 的实测认为，Nano Banana Pro 在真实感上仍然更好。

## 研究

### 3. OpenAI 在 GitHub 公开 722 篇数学论文，均由未发布的内部模型产出

OpenAI 10 月 6 日新建公开仓库 openai/math，一次放出 722 篇由未发布内部模型产出的数学论文，按相关性归为 372 个“结果族”，每族可能包含主结果、配套论证、推论或替代证明。据 The Verge 报道，新成立的独立顾问团体 AGMAI 表示，其中包括对“数百个”开放问题的解答。这批成果 OpenAI 9 月就预告过，当时称模型解决了 100 多个长期悬而未决的问题。这次改用 GitHub 仓库发布，并附上版本和引用规则，回应了数学界此前对其发布方式的批评。

- 产出方式：评测过程中共向模型提出约 4,000 个问题，绝大多数结果用同一流程得到，平均每个结果消耗相当于 ChatGPT Pro 约三小时的思考算力。
- 例外：黎曼 zeta 函数零点自由区和 CM 阿贝尔簇的 Hodge 猜想证明没有走固定流程，其中 Re(s) > 11/12 零点自由区的论文经过人工编辑以提升可读性。
- 验证状态不一：仓库自己说并非所有结果都有 Lean 形式化，未形式化的结果可能有问题；形式化目录目前列出 162 篇论文，后续会继续补充。
- 仓库还公开了 10 个结果的推理摘要，涉及 π 的无理性指数、Kaplansky 直接有限性猜想（特征 2）、自由群因子同构等；仓库采用 Apache 2.0 许可，修订会以新版本记录、旧版本保留。
- AGMAI 9 月底的建议要求 AI 实验室及时、尽量通过学术渠道发布结果，并披露模型名称、提示词和算力成本；OpenAI 表示仍在寻找符合这些要求的社区托管方式。

**为什么值得关注：** 结果数量已经超出数学界短期内能审读的规模，Tao 等人担心的“证明过载”开始成为现实，Lean 形式化覆盖率会是判断这批成果可信度的关键。对做形式化和自动定理证明的团队来说，这是一批规模空前的公开语料。

## 开源项目

### 4. Google 开源 EmbeddingGemma 2：7.4 亿参数，文本、代码、图像、音频、视频共用一个向量空间

Google DeepMind 10 月 6 日发布 EmbeddingGemma 2，把去年只支持文本的端侧嵌入模型扩展到代码、图像、音频和视频，所有模态映射到同一个向量空间。模型基于 Gemma 4 架构，共 7.4 亿参数，以 Apache 2.0 许可开源，目标是在手机和笔记本上本地完成搜索、检索和 RAG。比如用一段语音备忘去找视频片段，或用文字搜索几个小时的录音，都可以由一个模型离线完成。Google 称上一代下载量超过 2000 万次。

- 模块化设计：纯文本任务只需 2.7 亿参数，视觉编码器（1.7 亿）和音频编码器（3 亿）按需加载。
- 输出向量默认 768 维，借助 Matryoshka 表示学习可截断到 512、256 或 128 维，向量库存储最多减少约 6 倍。
- 上下文 8K token，是上一代的 4 倍，可一次处理约 5.5 分钟音频、29 张图片或 58 帧视频；量化后在 Pixel 11 Pro 上，纯文本约占 191 MB 内存，完整多模态约 567 MB。
- 代码检索提升最明显，MTEB Code 从 68.76 升到 78.68；与 Gemma 4 共用文本分词器和音频编码器，两者一起部署时总内存更低。
- 权重在 Hugging Face 和 Kaggle 提供，支持 transformers、sentence-transformers、llama.cpp、vLLM、Ollama、MLX、transformers.js 等，Unsloth 提供微调指南。

**为什么值得关注：** 想做本地代码检索、个人媒体库搜索或离线 RAG 的开发者，现在可以用一个不到 10 亿参数的模型覆盖多种模态，省掉为每种模态各配一个嵌入模型的麻烦。

来源：[Google 官方博客](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/) · [The Decoder](https://the-decoder.com/google-claims-embeddinggemma-2-outperforms-rival-embedding-models-twice-its-size/)

### 5. openTPU：AI 参与设计的开源推理加速器，在一块 Kintex-7 FPGA 卡上跑 Qwen3.5 和 Gemma 4

开发者 FeSens 开源了 openTPU，一个包含硬件 RTL、指令集、比特级精确模拟器、内核语言编译器和性能分析器的完整 AI 加速器项目，号称“由 AI 开发”。它延续了作者此前的 auto-arch-tournament 项目思路，那个项目让 Agent 反复提出微架构假设、验证并只合并跑分更好的方案，用来优化 RISC-V CPU。项目提交者在 Hacker News 上说，openTPU 用同样的递归改进循环，把最初每秒只能出几个 token 的设计提升到小模型每秒 80 多个 token。项目采用 Apache 2.0 许可，大部分工作只需 Python 和 Verilator，不需要 FPGA。

- 硬件是 Inspur YPCB-00338 卡（Xilinx Kintex-7 xc7k480t，两路 DDR3，峰值带宽 17.1 GB/s），设计跑在 133.33 MHz，包含四列脉动阵列矩阵单元。
- 实测解码速度（4-bit 权重）：LFM2.5-230M 每秒 85.8 token，Qwen3-0.6B 31.3，Qwen3.5-2B 12.09，Gemma 4 E2B 约 12；解码时 DRAM 带宽利用率达到峰值的 82% 至 94%，瓶颈在内存。
- 超出板载 4 GiB 的 MoE 模型可从主机流式加载专家，Qwen3.5-35B-A3B 能跑到每秒 3.95 token。
- 所有配置在卡上的输出与模拟器逐 token 一致；作者没有说明具体用了哪个模型、人工介入多少，HN 上也有评论认为这是“人指挥 LLM 做优化”，而不是 AI 自主设计硬件。

**为什么值得关注：** 这是一个可以从头读到尾的加速器教学项目，适合想了解推理芯片从 Python 内核到电路如何落地的工程师。它也展示了 Agent 加自动验证闭环在硬件设计上的潜力，但 AI 的实际贡献程度还需要更多披露。

来源：[openTPU GitHub 仓库](https://github.com/FeSens/openTPU) · [Hacker News 讨论](https://news.ycombinator.com/item?id=49980715) · [auto-arch-tournament 仓库](https://github.com/FeSens/auto-arch-tournament)

### 6. GitHub 为 Agent 重建 Git 存储架构：推送量一年涨 4.9 倍，内部测试写吞吐最高提升 35 倍

GitHub 首席工程师 Brian Celenza 10 月 6 日发文，说明 GitHub 正在为 Agent 时代重建 Git 基础设施。现有架构 Spokes 把每个仓库默认完整复制到 5 台文件服务器的本地磁盘，靠法定人数提交保证一致性，同一套副本既负责持久化又负责扩展读取，导致每加一个读副本，写入就更慢。Agent 在一个仓库里高频提交、数千个 CI 任务反复拉取同一分支，把这个矛盾放大了。新架构把存储和计算分开，权威数据放在 Azure Blob Storage，读请求由带缓存的轻量计算节点承担。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-07/6.svg" | relative_url }}" alt="GitHub 新 Git 架构的推送路径。接收推送 → 并行处理 → 引用更新 → 持久化存储 → 缓存读取 → 后台维护" loading="lazy"></figure>

- 增长数据：2025 年 9 月到 2026 年 8 月，Git 事件从每月 2182 亿次增至 4733 亿次；月推送量从 6.9 亿次增至 33.5 亿次（4.9 倍）。
- 2026 年 9 月单月提交 73.8 亿次，是一年前的 5 倍多；GitHub Actions 运行 32.6 亿次，是一年前的 4 倍多；PR 合并量接近一年前的 4 倍。最繁忙的单个仓库 8 月收到约 10 亿次请求。
- 设计原则一是只协调必须协调的部分，把推送的关键路径缩到引用更新这一步，对象存储、连通性校验、密钥扫描并行进行；压缩和垃圾回收移到独立的后台节点。
- 原则二是存储与计算解耦，计算节点故障更接近一次缓存未命中，可按流量弹性增减。内部基准中写吞吐最高提升 35 倍。
- GitHub 承诺保留分支保护、必需评审、审计日志等现有控制，后续文章会介绍具体架构；目前没有给出上线时间表。

**为什么值得关注：** 大规模运行编码 Agent 的团队，常常卡在推送延迟、单一主干引用上的合并竞争和 CI 拉取压力上。这篇文章给出了 GitHub 平台层的应对方向，自建 Git 服务的团队也可以参考。

### 7. Claude for Google Workspace 公测：在 Docs、Sheets、Slides 侧栏里直接改文件

Anthropic 10 月 6 日宣布 Claude for Google Workspace 在所有付费套餐开放公测，在 Google Docs、Sheets 和 Slides 里加了一个 Claude 侧栏，可以读取当前打开的文件和选中的内容，并直接在文件里修改。同时上线了 Google Docs、Sheets、Slides 三个连接器（beta），可以反过来在 Claude 对话里创建和编辑 Google 文件。侧栏里可用的模型、连接器和技能与 Claude 账户里一致。此前这个插件只在 Pro、Max、Team、Enterprise 套餐里内测。

- 编辑模式有两种，默认“编辑前询问”，每处改动以审批卡片展示，确认后才执行；“接受所有编辑”模式会连续完成任务、不再停顿。
- Docs 里可以就地改句子、调整标题样式且不破坏周围格式，大段改写以建议卡片形式给出；Sheets 里可写公式、建数据透视表和原生图表，复杂的连接和清洗可以把区域拉进 Python 处理后写回。
- Slides 里可按现有版式和主题生成新页面，并检查元素重叠、溢出页面或文字难读等问题。
- 从 Google Workspace Marketplace 安装，管理员可在 Google Admin 控制台按域或群组部署；Enterprise 套餐的 Compliance API、客户管理密钥（CMEK）和 OpenTelemetry 审计导出同样适用。

**为什么值得关注：** 主要在 Google 文档体系里办公的团队，不用再在 Claude 和文件之间来回复制粘贴，而且可以复用已有的技能和连接器。默认的逐条审批适合先小范围试用。

## 行业动态

### 8. Meta 与 Sierra 牵头制定 Personal Agent Protocol：让个人 Agent 用 OAuth 正式接入企业

客服 Agent 公司 Sierra 10 月 6 日宣布，与 Meta 及 Genesys、Instinct、Rocket、Shopify、Stripe、Walmart 等合作方共同制定开放标准 Personal Agent Protocol，规定个人 AI Agent 如何代表用户与企业打交道。现在多数个人 Agent 像人一样加载网页、点表单，失败了就去打客服电话，既慢又容易被网站的反机器人机制拦下。新协议的思路是由用户决定给 Agent 多大权限，由企业决定 Agent 能做什么，并让企业能识别出哪些流量来自谁的 Agent。TechCrunch 同日报道，Amazon 已开始屏蔽 Meta 的 Muse Agent，很多用户的 Agent 也在 Walmart 等网站的人机验证环节被挡住。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-10-07/8.svg" | relative_url }}" alt="Personal Agent Protocol 的会话流程。发现入口 → 访客会话 → 用户授权 → 选择通道 → 完成任务" loading="lazy"></figure>

- 流程从企业网站开始，Agent 先发现企业提供哪些接入方式，再以访客身份开启会话，可以查库存、问退货政策等。
- 需要访问账户时，用户在企业页面登录，或使用事先交给 Agent 的凭据，并决定 Agent 只读还是可写；会话基于 OAuth，跨渠道保持连续。
- 之后 Agent 可以按企业的选择走网页、基于 MCP 或 OpenAPI 的接口，或与企业自己的 Agent 对话（例如处理保修索赔）。
- Sierra 计划本月晚些时候发布 v0.1 规范，并提供参考实现、举办设计研讨会；更细的权限、推送通知、无需透露卡号的支付扩展还在规划中。

**为什么值得关注：** 做个人 Agent 和做电商、客服系统的团队，可能很快需要支持这套接入方式；在规范出来之前，Agent 被网站误拦的问题还会持续。值得注意的是，OpenAI、Google 和 Amazon 都不在这份合作方名单上。
