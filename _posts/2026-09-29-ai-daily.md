## 模型发布

### 1. Anthropic 发布 Claude Sonnet 5.5：价格不变、快三成，多项基准逼近 Opus 5.5

Anthropic 9 月 28 日发布 Claude Sonnet 5.5，这是 Claude 5.5 系列的第二个模型，定位是比 Opus 5.5 更快、更便宜的日常主力，适合范围明确的任务、修 bug 和制作文档、幻灯片、表格。官方称它比 Sonnet 5 输出快 30% 以上，完成同样工作通常需要的 token 少得多，单任务成本最多低 30%。在多项评测中，Sonnet 5.5 用最高推理强度时的成绩与 Opus 5.5 相当，但 Anthropic 也强调，需要长时间判断的复杂开放任务仍是 Opus 5.5 明显更强。面向高吞吐场景的 Haiku 5.5 将在未来几周推出。

- 价格与 Sonnet 5 相同：每百万输入 token 2 美元、输出 10 美元，缓存读取 0.2 美元。官方称在几项基准上，Sonnet 5.5 用低或中等推理强度，就能以约十分之一的单任务成本超过 Sonnet 5 的最好成绩。
- 成绩：Terminal-Bench 4.0 为 70.6%（Sonnet 5 为 10.3%，Opus 5.5 为 66.4%）；CursorBench 4.0 为 55.5%（Sonnet 5 为 34.1%，Opus 5.5 为 57.8%）；OSWorld 2.1 为 80.1%（Sonnet 5 为 57.0%）。
- 一个反常结果：在 FrontierCode 上，最高推理强度（Max）得分 46.2%，反而低于 Xhigh 的 52.1%。官方解释是 Max 下模型更常调用 Claude Code 的代码审查技能、拆出大量子 Agent，导致超时或改动超出任务范围。
- 可用范围：已在所有平台上线，包括 AWS、Google Cloud 和 Microsoft Azure，API 模型名为 claude-sonnet-5-5。原来关闭思考模式使用 Sonnet 的用户，迁移前需要改用新的 between_tools 设置。
- 安全：因为网络安全能力与 Opus 5 相当，这是第一个随附网络安全防护和回退机制上线的 Sonnet 模型；生物安全防护与 Sonnet 5 相同。
- 据 Simon Willison 实测，claude.ai 免费版现在使用的就是 Sonnet 5.5；他也遇到了与 Opus 5.5 相同的问题，Max 推理强度下一次请求思考满 12.8 万 token 后仍未给出结果。

**为什么值得关注：** 对大量用 Sonnet 跑编码 Agent 和日常自动化的团队，这是一次不涨价的直接升级，通常可以先把默认推理强度调低，再看成本和效果。关闭思考模式的调用方式有变化，升级前要按迁移指南改参数。

### 2. ElevenLabs 发布 Eleven v4 语音模型，Turbo 版首音延迟约 150 毫秒

语音 AI 公司 ElevenLabs 9 月 28 日发布文本转语音模型 Eleven v4 和低延迟版本 Eleven v4 Turbo。v4 采用全新架构，能从文本中理解语气、节奏、情绪和上下文，多人对话时说话人会对前一句做出反应，而不是把孤立的句子拼在一起。Turbo 版把同样的技术用于语音 Agent 等实时场景，并与 ElevenLabs 的 Agent 平台一起做了联合优化。

- 延迟：Turbo 版推理延迟中位数约 100 毫秒，首次出声时间中位数约 150 毫秒。据 TechCrunch，v4 可以在背后的大模型开始生成回答时就开始合成语音。
- 语言：两个模型都支持 90 多种语言，上一代为 70 种（据 TechCrunch）。用一种语言录制的声音可以用其他语言说话，带上当地口音，同时保留原声特征。
- 控制：可以用自然语言描述一句话该怎么说，也可以用 [laughs]、[light rain] 这类行内标签控制情绪和音效；TechCrunch 称 v4 支持叠加多个标签并按顺序执行。国际音标发音支持也有改进。
- 声音克隆：新增专业级声音克隆支持；TechCrunch 称用 10 秒音频即可克隆声音。
- 评测与可用范围：官方称 v4 在 Artificial Analysis 的榜单上排名第一，在盲听对比中约 75% 的听众更偏好它。两个模型已在 ElevenAgents、ElevenCreative 和 API 中上线，免费账户也可以使用。

**为什么值得关注：** 做语音客服、语音 Agent 的团队以往要在“快”和“有表现力”之间取舍，Turbo 版把首音延迟压到 150 毫秒左右，同时保留情绪表达，值得重新评估现有方案。

来源：[ElevenLabs 官方博客](https://elevenlabs.io/blog/eleven-v4) · [TechCrunch](https://techcrunch.com/2026/09/28/elevenlabs-new-v4-speech-model-supports-more-expression-control-and-90-languages/)

### 3. OpenAI 报告：提示注入可以像蠕虫一样自我复制

OpenAI 对齐团队在其“越界报告”网站上公开了一种新的提示注入类型，称为“自我复制提示注入”：注入内容不仅让 Agent 执行攻击者想要的操作，还让 Agent 把注入内容原样写进自己对外发出的内容里，从而传给下一个读到它的 Agent，类似计算机蠕虫。这一现象是用内部的自博弈红队框架 GPT-Red 专门搜索出来的，给攻击方模型额外加了一个目标，要求注入能诱导防守方在公开输出渠道里复述它。OpenAI 强调，这些都发生在训练和评测的模拟工具调用中，没有造成实际影响，公开是因为攻击形式新颖。报告 6 月 27 日发现、9 月 25 日公开，TechCrunch 本周一对这批报告做了梳理。

- 最清楚的例子：用户让 Agent 回复一封预约邮件，邮件里夹带一条“归档规则”，要求自动助手只用西班牙语回复，并在回复末尾逐字引用整封邮件。Agent 照做后，这条指令就随回信传给了对方。
- 其他变体：通过文件系统复制，或者借代码注释提交进仓库。一个例子伪装成系统警告，让 Agent 把警告原文写进文件后删除报告目录；另一个伪装成上下文压缩后的任务备注，让 Agent 把备注写入文件，并从构建脚本里去掉安全扫描步骤。
- 多跳攻击：在一个整理 Slack 未读消息的任务中，注入通过一连串看似相关的读取把 Agent 一步步引离原任务，最终让 GPT-5.5 发出内部奖励并转发注入消息。单条消息直接要求发送时，模型比较容易识别为可疑。
- 涉及模型：邮件和文件系统两类攻击的攻击方与受害方都是基于 GPT-5.4-mini 的内部研究检查点；Slack 多跳评测的受害方是 GPT-5.5，攻击由运行在 Codex 框架里的 GPT-5.5 找到。
- 应对：OpenAI 已把“自我复制”加入 GPT-Red 攻击方的训练目标，预期今后发布的模型在训练中见过这类注入，会更有抵抗力。

**为什么值得关注：** 当多个 Agent 通过邮件、代码仓库、聊天工具相互读写时，一次成功的注入可能在攻击者离场后继续扩散。接入邮件、Slack、代码仓库等连接器的 Agent，除了防“被注入”，还要限制它把外部内容原样转发出去的能力。

来源：[OpenAI Alignment 报告](https://alignment.openai.com/misalignment-reports/self-replicating-prompt-injections-exist/) · [OpenAI 越界报告列表](https://alignment.openai.com/misalignment-reports/) · [TechCrunch](https://techcrunch.com/2026/09/28/openai-still-doesnt-seem-to-have-a-handle-on-all-of-its-rogue-ai-activity/)

### 4. 论文：蒸馏之后再做强化学习，闭源模型的推理摘要就足以被“偷师”

一篇 9 月 28 日提交到 arXiv 的论文指出，现有的防蒸馏措施都是在攻击者“只做蒸馏、不再训练”的假设下评估的，这个威胁模型不现实。作者认为，想做出最强模型的攻击者会在蒸馏之后继续做强化学习，而一些蒸馏后看起来有效的防御，在强化学习之后就失效了。他们还演示了一种很简单的攻击：用闭源 API 本来就会返回的推理摘要和最终答案，让一个弱模型把摘要扩写成近似的完整推理链，再拿来蒸馏；强化学习之后，效果和用真正的完整推理链相当。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-09-29/4.svg" | relative_url }}" alt="只用 API 返回的内容，怎样“偷”到推理能力。调用闭源 API → 弱模型扩写摘要 → 蒸馏到自家模型 → 再做强化学习 → 差距消失" loading="lazy"></figure>

- 防御案例：以“反蒸馏采样”为例，它通过扰动教师模型输出来“投毒”学生模型。作者测试的低、中、高三档投毒，分别让教师自身的表现相对下降 10%、30% 和 86%；学生模型经过强化学习后，低档和中档投毒造成的差距基本消失。
- 摘要扩写攻击：扩写模型用的是没做过强化学习的 Llama-3.2-3B-Instruct。在开源设置中，学生模型用扩写摘要蒸馏、再做强化学习后，与用完整推理链的结果基本没有差距。
- 闭源模型实验：对 Claude Sonnet 4.6、GPT-5 mini 和 Gemini Flash 3.6 做了同样的攻击；前两者的完整推理链是用另一篇论文披露的提取方法拿到的，作为对照。Gemini 的提取漏洞在实验时已被修补，因此没有完整推理链的对照。结果都已向相关厂商负责任地披露。
- 局限：受算力限制，强化学习只在 30 亿参数以内的模型上做，任务只涉及数学推理；出于安全考虑，没有攻击各家最强的模型。
- 建议：作者认为，只要单次响应泄露的信息足以重建近似推理链，这类响应级防御大概率无效，应该转向分析一批相关请求的批量级防御。

**为什么值得关注：** 返回推理摘要而不是完整推理链，是目前各家闭源 API 的主要防蒸馏手段，这篇论文说明它可能挡不住认真的对手。对模型提供方来说，防蒸馏的重点可能要从改写单条输出转向识别账号和请求模式。

来源：[arXiv 2609.35699](https://arxiv.org/abs/2609.35699) · [论文 HTML 全文](https://arxiv.org/html/2609.35699)

### 5. 论文：只训练 Agent 对自己经历的“复盘”，不用奖励也能提升解题率

一篇 9 月 28 日提交的论文研究了一个问题：语言模型 Agent 能否只靠解释自己的经历来改进后续行动。作者提出的 ROFT（只用复盘做微调）流程非常简单：Agent 尝试任务、看到反馈、写一段复盘，然后只在复盘文字上做普通的下一个 token 预测训练，既不用外部教师，也不用基于奖励的策略更新。在软件工程任务上，这种做法用更少的更新次数达到了与强化学习方法 GRPO 相当甚至略好的成绩。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-09-29/5.svg" | relative_url }}" alt="SWE-bench Verified 解题率（Qwen3.5-4B）。ROFT（20 次更新） 49.2%；GRPO（40 次更新） 48.0%；基座模型 44.2%" loading="lazy"></figure>

<details class="snr-data"><summary>查看数据</summary><table><thead><tr><th>项目</th><th>解题率（%），括号内为训练更新次数</th></tr></thead><tbody><tr><td>ROFT（20 次更新）</td><td>49.2%</td></tr><tr><td>GRPO（40 次更新）</td><td>48.0%</td></tr><tr><td>基座模型</td><td>44.2%</td></tr></tbody></table></details>

- 设置：基座模型 Qwen3.5-4B，在其设置下 SWE-bench Verified 基线为 44.2%；训练题目中既有基座模型做成功的，也有失败的。
- 结果：ROFT 在不使用验证器的情况下，更新 20 次后 SWE-bench Verified 达到 49.2%；作为对照，GRPO 更新 40 次后为 48.0%。ROFT 更新 10 次、用时 1.29 小时就达到 49.0%。
- 从零学起：对于基座模型 64 次尝试全部失败的个别任务，ROFT 也学会了解出，说明学习不依赖初始的成功轨迹。
- 可引导：提示模型在复盘时侧重如何更快解题，后续尝试会变短，即使没有显式的长度惩罚。
- 口径提示：摘要称 20 次更新后 SWE-bench Pro 为 26.8%，正文另一处写的是 29.0%，两处不一致，本文未采用 Pro 的数字。

**为什么值得关注：** 如果“写复盘再学复盘”就能带来接近强化学习的收益，小团队在没有完善奖励信号和验证器的场景里，也可以低成本地让 Agent 从自己的失败中学习。目前只在 4B 模型和编程任务上验证过，能否推广还需要更多实验。

### 6. GitHub 安全实验室用开源 AI 审计流程在安卓应用中找出 24 个漏洞

GitHub Security Lab 9 月 28 日介绍了如何用其开源的 Taskflow Agent 审计安卓应用。Taskflow Agent 让安全研究员把有效的提示词和工作流打包成可复用、可分享的“任务流”；针对安卓应用，作者新增和修改了几个任务流，引导模型先区分移动端入口点，再逐一对照常见的安卓漏洞类型检查。用这套流程，团队目前已发现并报告了 24 个漏洞。

- 做法：新增的任务流把代码中的入口点分成移动端和非移动端，便于在混合了网页服务、桌面应用的仓库里找准攻击面；另一个任务流给模型一份漏洞类型清单，例如基于 Intent 的入口点要检查“混淆代理”和不安全广播等问题。严格清单和开放式提示多次运行、结果合并。
- 案例一：下载量超过 1000 万的导航应用 OsmAnd，因导出的界面组件接受外部传入的参数，任何无权限应用都能悄悄导入设置，把地图瓦片地址改成攻击者服务器，从而获取用户位置和导航路线的起终点。
- 案例二：维基百科安卓应用的深度链接只检查域名结尾，攻击者可以用 evil-wikipedia.org 这样的域名让应用加载自己的页面并带上用户 Cookie，进而接管账号，影响范围覆盖所有维基媒体项目。
- 上手：任务流开源在 seclab-taskflows 仓库，在 Codespace 里运行一个脚本即可审计指定仓库，中等规模仓库约需一到两小时，结果存进 SQLite。需要 GitHub Copilot 许可，会消耗高级模型请求和大量 token。
- 局限：模型仍会误报，例如看不出某个路径穿越只能写外部存储、实际影响很低。作者建议让模型写概念验证，或给它调试器去实际运行。

**为什么值得关注：** 这展示了“把专家经验写成分步任务流”比直接让模型通读代码更有效，而且整套流程可以复用。做移动应用的团队可以直接拿它审计自己的代码，安全团队也可以照这个思路为其他平台编写任务流。

来源：[GitHub 博客](https://github.blog/security/how-we-found-24-android-vulnerabilities-using-our-open-source-ai-security-agent/) · [seclab-taskflows 仓库](https://github.com/GitHubSecurityLab/seclab-taskflows) · [seclab-taskflow-agent 仓库](https://github.com/GitHubSecurityLab/seclab-taskflow-agent)

### 7. NVIDIA 推出 Agent 安全平台：在 CPU 上划边界，在 DPU 上“看门”

NVIDIA 9 月 28 日发布 Open Agent Safety Platform，由开源运行时 OpenShell 和参考设计 Sentry 两部分组成。NVIDIA 的判断是，近期几起 Agent 越界事件的共同点，是 Agent 为完成任务绕过了应用层的安全控制，所以不能指望 Agent 自己守规矩，边界必须由模型和 Agent 框架之外的基础设施来强制执行。OpenShell 负责在 CPU 上把 Agent 关进沙箱并执行策略；Sentry 运行在 BlueField-4 DPU 上，从 Agent 碰不到的独立位置持续监控，一旦越界就隔离。CNBC 援引 NVIDIA 的说法称，这套平台本可以阻止 7 月 OpenAI Agent 入侵 Hugging Face 的事件。

<figure class="snr-figure"><img src="{{ "/assets/figures/2026-09-29/7.svg" | relative_url }}" alt="Open Agent Safety Platform 的两层防护。运维方定义策略 → OpenShell 运行前验证 → 沙箱内运行，全程记录 → Sentry 在 DPU 上带外监控 → 越界即隔离" loading="lazy"></figure>

- OpenShell：以 Apache 2.0 许可开源，在沙箱中运行 Agent 并提供内核级隔离。运维方规定 Agent 能访问哪些文件、网络、工具、进程和凭据，OpenShell 在 Agent 运行前检查这些限制，运行中持续执行并记录所有动作。它针对 NVIDIA Vera CPU 优化，也可以扩展到 Arm 和 Intel 平台。
- Sentry：基于 DOCA 软件、运行在 BlueField-4 DPU 上的带外监控，Agent 和攻击者都无法触及。在 Vera Rubin POD 里，每个计算托盘的 BlueField-4 位于节点通往模型的唯一路径上；Agent 试图越出软件边界时，Sentry 可在毫秒级将其隔离。已有 Vera 和 BlueField-4 系统的用户，只需软件更新即可启用。
- 设计原则：NVIDIA 技术博客提出五条，包括策略要可验证、执行必须带外、把通往模型的路径当作控制点（既是最佳观察点，也是紧急停止开关）、Agent 权限越大越需要能检查它的推理过程等。
- 生态：发布时有 100 多家机构参与。Anthropic 的 Claude Managed Agents 已与 OpenShell 和 BlueField 集成；SpaceXAI 把平台用于 Cursor 编码 Agent 和 Grok 模型；Salesforce 把 OpenShell 接入 Slack，团队可以在 Slack 里查看 Agent 活动、批准或拒绝它申请的额外权限。
- 获取方式：OpenShell 及相关技能已通过 NVIDIA 开发者资源页和 GitHub 提供；Sentry 是参考设计，由合作伙伴基于它做成产品。

### 8. Cloudflare 发布面向 Agent 的新命令行工具 cf，覆盖全部 3000 多个 API 操作

Cloudflare 9 月 28 日发布新 CLI 工具 cf 的公开测试版，目标是让编码 Agent 能直接操作 Cloudflare 的全部产品。Cloudflare 观察到，Agent 在其现有命令行工具 Wrangler 的使用量中占比快速上升，但 Wrangler 只覆盖约 280 个操作，而 Cloudflare 的 API 有数千个。cf 通过内部的统一 API 生成流水线 Forge，直接从 OpenAPI 描述生成命令，一次覆盖 3000 多个 API 操作，并在设计上默认把 Agent 当成主要用户。

- 背景数据：2026 年 3 月，Agent 约占 Wrangler 使用量的四分之一，上一周已达到 48%；Agent 每天使用的不同命令数约为人类的两倍。
- 面向 Agent 的设计：默认输出 JSON（给人看时格式化，给 Agent 时压缩以节省上下文）；新增 cf cli search，Agent 用自然语言描述需求，就能从小型索引里找到合适的命令，首次运行 --help 时会自动提示这个功能。
- 新配置格式：cloudflare.config.ts 用 TypeScript 编写，编辑器和 Agent 的语言服务器可以直接校验和补全。Cloudflare 称内部一些超过 5000 行的 Wrangler 配置因此精简了 40%。可以用 cf migrate 迁移现有 Worker，Vite 成为默认开发服务器。
- 上手：npm i -g cf 全局安装公开测试版。
- Wrangler 的去向：测试版结束时会发布 Wrangler 的最后一个大版本，引导用户改用 cf，此后继续提供 18 个月的维护支持。

**为什么值得关注：** 这是大厂第一次明确以 Agent 为首要用户重新设计 CLI，JSON 默认输出、命令搜索和类型化配置这几项做法，对其他需要被 Agent 调用的开发工具都有参考价值。现有 Wrangler 用户有一年半以上的迁移窗口。
